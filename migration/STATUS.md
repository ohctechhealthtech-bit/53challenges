## Remaining

### ~40 portable functions

Every one needs the same treatment: port, predict the output from
`migration/data/`, diff against the live Base44 response, deploy, verify on
127.0.0.1, then route in nginx. Each of the first eight had exactly one defect
that appeared only against the real database, so the verification step is not
optional overhead — it is what has caught every bug so far.

### 13 functions blocked on missing services

| Blocker | Functions | Needs |
|---|---|---|
| Plesk API | provisionDomain, createChallengeSubdomain, deleteChallengeSubdomain, applyNginxDirectives, pleskDiagnostic, pleskCreateKey | Plesk REST credentials |
| Email | hostPortal, hostChallengeRequest, guardianStatusNotify, marketingHub | SMTP host, or SendGrid/SES |
| LLM | marketingHub, hostChallengeRequest, participantPromo, planChallengeFromProposal | Anthropic or OpenAI key |
| File storage | provisionDomain, manageAdminSsl | keep media.base44.com, or move to S3 |
| Image generation | marketingHub, participantPromo | a provider |

No amount of code removes these. They need infrastructure decisions first.

### The entity API — not yet scoped

The frontend does not only call functions. It calls Base44's generic entity
REST API directly for **32 entities**:

```
GET  /api/apps/{id}/entities/SiteSetting
GET  /api/apps/{id}/entities/Score?q={...}&sort=-created_date&limit=5
PUT  /api/apps/{id}/entities/JudgingPanel/{id}
```

Leaving Base44 completely means reimplementing that: its query syntax, its
sort and limit handling, and the row-level security rules on 34 entities —
which Base44 enforced declaratively and Java must enforce in code. This is
comparable in size to all the functions put together and is the single largest
remaining unknown.

There is a shortcut worth considering: rewrite those 32 call sites in the
frontend to use purpose-built endpoints instead, which is less work than a
faithful clone of a generic API and removes the RLS-parity risk entirely.

## Bugs found so far, and what they cost

Each appeared only when real code met the real database.

| Bug | Would have caused |
|---|---|
| `characterEncoding=utf8mb4` in the JDBC URL | no database access at all |
| `/api/health` never touched the datasource | the above, undetected — reported as "verified" |
| `excluded` nullable, compared with `= false` | every vote count zero, site-wide |
| bare `new ObjectMapper()` | every entity response 500 |
| `JsonNode.valueStream()` (Jackson 2.19+) | build failure on the server |
| `limit` over 10000 on export | silent data loss in the backup |
| timestamps without `Z` parsed as local time | 1784 timestamps shifted 5.5 hours |
| Spring's generated security password | a live credential printed to the journal |

## Method

Deploy the jar, verify on `127.0.0.1:8081`, *then* add the nginx block. Until
the block exists the endpoint is unreachable from outside, so a broken build
affects nobody. Rollback is deleting four lines of nginx config — no rebuild,
no restart, no redeploy.

Each function is mounted at its original Base44 URL
(`/api/apps/{appId}/functions/{name}`), which is why none of this has needed a
frontend change.
